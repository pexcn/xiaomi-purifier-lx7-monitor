# TL;DR：目前知道什么

更新：2026-11-07。设备：小米净水器 500G 增强版 MR532-D，`yunmi.waterpuri.lx7`。

**已还原插件的滤芯寿命显示公式；尚未恢复 MCU 的流量累计算法。F1/F2 的 usedflow 计量水路、单位，以及 3600L/7200L 的关系仍无定论。**

## 已证实

### 样本与版本

| 来源 | 已确认内容 | 证据 |
|---|---|---|
| 实机（用户提供） | `fw_ver=2.1.3`、`mcu_fw_ver=0012`、`hw_ver=esp8266`；与 App 显示的 `2.1.3.0012` 相符 | [脱敏版本记录](evidence/runtime-version.json) |
| 仓库固件 | ESP8266 / Xtensa 小端 Wi-Fi OTA 镜像，内嵌版本 **1.3.9**；不是实机当前版本 | [固件分析](firmware.md)，`FUN_402409EC`，版本字符串文件偏移 `0x6D730` |
| 上传的米家插件 | 型号声明仅含 lx7，型号映射版本 75、工程版本 1.0.62；拆出 639 个有效模块 | [插件来源记录](evidence/plugin/provenance.json)，`model_list.json`、`android/project.json` |

插件版本不等于固件版本，也未证明上传包就是手机当前激活的版本。旧固件的函数地址和实现不能直接套用到实机 2.1.3。

### 滤芯读数与寿命显示

插件将 **F1 对应复合滤芯，F2 对应 RO 滤芯**。下表来自用户两次八字段查询；两次之间有用户自行重置，不能相减作为连续用量。

| 字段 | 最初读数 F1 / F2 | 重置后读数 F1 / F2 | 已知含义 |
|---|---|---|---|
| `usedtime` | 0 / 0 | 24 / 24 | 插件按小时解释；MCU 累计方式未知 |
| `usedflow` | 0 / 0 | 10 / 10 | 使用流量字段；单位和计量水路未知 |
| `totaltime` | 8640 / 17280 | 8640 / 17280 | 插件解释为 360 / 720 天 |
| `totalflow` | 7200 / 7200 | 7200 / 7200 | 两支均为 7200；没有字段返回 3600，单位未知 |

证据：[用户观察记录](evidence/usedflow-observations.json)、[字段顺序](usedflow.md#八项返回值)；插件模块 10142 的 `Base.getFilterData`、10334 的 `DealProp.excute/getDays`，见 [原文摘录](evidence/plugin/excerpts.md)。

**插件首页和详情页的寿命百分比按时间余量计算：**

```text
剩余百分比 = (totaltime - usedtime) × 100 / totaltime
```

负数归 0，首页用 `parseInt` 显示整数；上述重置后读数对应两支都显示 99%。lx7 隐藏剩余天数字样。所查显示链没有将 usedflow/totalflow 纳入此公式，**但 MCU 生成 usedtime 时是否考虑流量仍未知**。

证据：[插件寿命公式](plugin.md#时间与滤芯寿命)，模块 10334、10298 的 `MainPageFilter.render`、10436 的 `FilterState`。

### 私有接口与隐藏设置

| 项目 | 已确认内容 | 证据 |
|---|---|---|
| `get_prop` | lx7 插件读取 15 项，覆盖滤芯、TDS、温度、冲洗、告警阈值和灯模式；不是设备全部属性清单 | 模块 10136，`MainPage.readState` |
| TDS 阈值 | 用户 `set_tds_warn_thd [50]` 成功；插件有 100–300、步长 10 的选择器函数，但当前 render 未见入口，不能当作固件范围或默认值 | 用户实测 U2；模块 10139，`showTdsList` |
| 灯模式 | 用户 `set_lightMode ["1"]` 成功；插件发送数字 `[0]`/`[1]`。插件特殊模式还检查出水 TDS≥阈值和冲洗状态；硬件灯光行为未实测 | U2；模块 10391 的 `setMode`、10334 |
| 隐藏入口 | lx7 启用在 4 秒内连点“功能设置”标题 5 次显示灯模式开关的代码 | 模块 10286、10391，设置路由 `10007→10385→10391` |
| 滤芯复位 | 插件在两次确认后请求 `set_f1_used` / `set_f2_used`，参数 `[0,0]`；两个参数的具体含义和存储行为未知 | 模块 10436，`resetTwice/setResetMode`；本分析未执行 |

完整参数、限制和证据见 [MiIO 接口表](miio-api.md) 与 [插件原文](evidence/plugin/excerpts.md)。主动冲洗命令尚未恢复，不能按属性名猜 setter。

### Wi-Fi 桥接与历史水量

- **旧固件的已恢复通用桥接路径不计算滤芯流量**：未匹配本地处理器的方法进入 MCU 下行队列，返回值再封装成 JSON。证据：[usedflow 静态追踪 S1–S8](usedflow.md#静态追踪)，`FUN_4024C4F4 → FUN_4024C2D8 → FUN_4024CBFC`、`FUN_4024B4E8`。未识别出独立 MCU 镜像，不能据此断言下载包绝不含任何 MCU 数据。
- **历史用水与滤芯 usedflow 是不同数据链**：插件通过云端 SDK 读取 `pure_water_record` 及日/周/月统计，历史水量除以 1000 显示 L；不能把这一单位套给 usedflow。lx7 统计图主动将废水显示置 0，不能据此认定没有废水。证据：[历史记录解析](plugin.md#usedflow容量与历史水量)，模块 10316 的 `getItem`、10319 的 `getPureWaste`、10142 的 `Base.formatWater`。
- `miIO.info.life` 是运行计时，**不是滤芯寿命**。证据：[计数与保存分析](usedflow.md#计数保存及复位已找到什么)，旧样本 `FUN_40240F28 → FUN_40241BFC → FUN_40241B60`。

## 推测与待验证

| 问题 | 当前判断 |
|---|---|
| 是否按 24 小时、10L 向上取整？ | **推测**。用户重置后不足 24 小时、仅取几升水却读到 24/10，与分档模型相容；尚无连续跳变数据，连流量单位也未确定 |
| F1/F2 都是 10，是否证明计量相同？ | **不能证明**。粗粒度可能使不同水量落在同一档 |
| 7200 是否等于 3600L 纯水加等量废水？ | **待验证**。没有恢复此换算；需要 3600L 的原始标称来源和独立体积对照 |
| 流量算法在哪里？ | **推测主要在独立 MCU**。当前缺少同版本 MCU 代码；传感器位置、脉冲系数、冲洗计入方式、持久化及复位实现均未知 |

以上假设、候选公式和限制见 [usedflow.md](usedflow.md)。

## 下一步

1. 编写只读采样脚本，记录时间、滤芯计数和工况，观察自然发生的 `10→20→30`、`24→48` 跳变。
2. 正常用水时同步记录实际纯水体积，并对照云端历史事件；不专门耗水，不再次重置滤芯。
3. 若要区分原水与纯水口径，仍需独立原水/废水计量或 MCU 证据；单靠纯水量和未知比例计数可能无法唯一判定。

目前仅进行了静态分析；设备响应来自用户提供。本分析未执行设备查询、设置、冲洗、复位或刷机，也未查询云端历史记录。
