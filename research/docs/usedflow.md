# usedflow：口径与证据边界

**版本范围**：静态追踪只针对仓库 `1.3.9`。用户后续 `miIO.info` 确认当前实机报告 `2.1.3 / MCU 0012`，见 [版本核对](firmware.md#实机版本核对)。不能把旧版桥接路径当成当前版实现证据；U1/U2/U3 的现场结果保留其用户实测来源，未获得将其读取时间与固件版本独立绑定的抓包。

## 结论

**已证实**：用户提供的请求中，`f1_totalflow`、`f2_totalflow` 都返回 `7200`；`8640/17280` 对应的是 `totaltime`，不是两个流量值。检查用户 `mit` fork 的 raw 实现，没有将流量乘 2 或重排数组。

**已证实**：样本 Wi-Fi 固件的通用方法下发与 MCU 应答路径没有按 F1/F2 进行累计或纯废水换算；它搬运 JSON/参数文本。

**推测**：`usedflow` 的设备专用累计逻辑在独立 MCU。**待验证**：F1/F2 分别累计原水、纯水还是含冲洗的其他水量；不能从本样本给出确定答案。

**已证实（新增插件证据）**：用户上传的 lx7 插件按小时解释 usedtime/totaltime，以时间余量计算首页滤芯百分比；详情页沿用该值。所查显示链不使用 usedflow/totalflow。它没有解释 F1/F2 的实际计量水路，也未证实 10L 分档。见 [plugin.md](plugin.md) 和 [模块原文](evidence/plugin/excerpts.md)。

**已证实（用户实测 U3 及后续时序补充）**：重置后，F1/F2 的 usedtime、usedflow 均为 0；随后经过十几个小时、仅取用几升纯水，相同查询返回 `[24,24,10,10,8640,17280,7200,7200]`。**用户推测**：不足 24 小时按 24 小时算、时间步进为 24，用量步进为 10。插件按小时解释时间；后续跨档边界、流量单位和精确取整规则仍待验证。

## 八项返回值

证据 U1：用户在本次会话提供的命令和返回数组；本次分析没有执行该命令。DID 在文档中用占位符替代。

```sh
mit --json raw "$DID" get_prop '["f1_usedtime","f2_usedtime","f1_usedflow","f2_usedflow","f1_totaltime","f2_totaltime","f1_totalflow","f2_totalflow"]'
# 用户提供的结果：
# [0,0,0,0,8640,17280,7200,7200]
```

| 下标 | 请求字段 | 返回值 | 已确认内容 | 未确认内容 |
|---:|---|---:|---|---|
| 0 | `f1_usedtime` | 0 | F1 使用时间字段的读数；插件按小时解释 | MCU 累计条件和更新时间 |
| 1 | `f2_usedtime` | 0 | F2 使用时间字段的读数；插件按小时解释 | 同上 |
| 2 | `f1_usedflow` | 0 | F1 使用流量字段的读数 | 原水/纯水、单位、量化步长 |
| 3 | `f2_usedflow` | 0 | F2 使用流量字段的读数 | 同上 |
| 4 | `f1_totaltime` | 8640 | F1 总时间字段；插件解释为 360 天 | 是否额定/配置寿命，默认值来源 |
| 5 | `f2_totaltime` | 17280 | F2 总时间字段；插件解释为 720 天 | 同上 |
| 6 | `f1_totalflow` | 7200 | F1 总流量字段的读数 | 单位、额定/配置含义、是否原水容量 |
| 7 | `f2_totalflow` | 7200 | F2 总流量字段的读数 | 同上 |

以上字段对应关系依据用户请求顺序，不是从 MCU 固件恢复的字段表。尚未获得独立解密抓包来再次核对设备返回顺序。四个 0 也不能单独证明设备全新、滤芯已复位或没有实际用水。

### 重置后读数与分档假设

证据 U3 及用户后续补充：用户明确重置后立即读数为 0，十几个小时、取用几升纯水后变为 24/10；不是重置立即得到 24/10。见 [usedflow-observations.json](evidence/usedflow-observations.json)。这一观察区间内没有再次重置；重置是用户自行进行，本分析没有执行。尚无精确采样时间、实际取水体积和首次跳变时刻，不能据两个端点确定更新周期。

| 字段 | U3 读数 | 用户描述及判断 |
|---|---:|---|
| `f1_usedtime` / `f2_usedtime` | 24 / 24 | 重置后立即为 0，十几个小时后为 24；支持不足 24 小时按一档计算、步进 24 的猜测 |
| `f1_usedflow` / `f2_usedflow` | 10 / 10 | 重置后立即为 0，仅取用几升纯水后为 10；支持步进 10 的猜测，但不等于测得实际消耗 10L |
| `f1_totaltime` / `f2_totaltime` | 8640 / 17280 | 与 U1 相同；仍与 360×24、720×24 的时间配额假设相容 |
| `f1_totalflow` / `f2_totalflow` | 7200 / 7200 | 与 U1 相同；单位和原水/纯水口径仍未恢复 |

**推测，待跨档数据验证**：一种相容的上报模型是 `T报 = 24 × ceil(t / 24)`、`F报 = 10 × ceil(V / 10)`，其中插件已支持时间按小时解释，流量按升仍是假设。这是验证用候选公式，**不是反编译结果**。重置后立即为 0，排除了“重置立即上报 24/10”的描述；但按日历日记龄、首次更新时计入一档或其他流量单位仍可能解释观察，尚不能认定后台保存和实际传感器也只有这种精度。

两个 usedflow 同为 10，不能证明两滤芯累计同一种水。例如仅在上述候选模型成立时，实际纯水 3L、原水 6L 都会报 10；粗粒度可能掩盖计量口径差异。

后续沿用当前状态，在正常用水中记录 `10→20→30` 的真实跳变及累计纯水量；有现成条件则同时记录废水量。不必再次重置或专门耗水。时间字段记录下一次 `24→48` 的时点，与原重置时刻、跨午夜和满 24 小时分别比较，区分日历日与滚动时间档。尚未收集这些边界数据。

### 时间和流量不要混淆

`8640 = 360 × 24`、`17280 = 720 × 24`。**已证实（插件约定）**：模块 10334 的 `getDays` 将剩余时间除以 24，支持二者按小时表示、对应 360 天和 720 天。MCU 如何生成使用时间仍未知。它们不是 8640L/17280L，也不是纯废水比。

### App 的寿命显示公式

模块 10142 明确将 lx7 归入两滤芯分支；模块 10334 的 `DealProp.excute` 对 F1/F2 分别计算 `(totaltime-usedtime)×100/totaltime`。模块 10298 的 `MainPageFilter.render` 再用 parseInt 显示整数百分比，详情页接收同一 leftPercent，没有额外读取流量计算百分比。

U3 的 usedtime=24 时，两个百分比分别约为 99.7222% 和 99.8611%，首页均显示 99%。内部剩余天数为 359/719；lx7 配置 showRestDays=false，不能声称页面一定显示这些天数。负数先归 0，NaN 显示 --。

这确认的是插件显示链没有做流量/时间余量取最小值，**不证明 MCU 在生成 usedtime 时未计入流量因素**。源码摘录和模块偏移见 [plugin.md](plugin.md)。

### 3600L 与 7200L

**已证实**：本次用户读数给出两个 `totalflow=7200`；没有字段返回 3600。ASCII/UTF-16 明文检索没有命中字符串 `3600`、`7200` 或这些字段名，见 [interfaces.json](evidence/interfaces.json)。这不等于数值常量绝不存在。

**已证实（客户端范围）**：`pexcn/mit` 提交 `f0760df508e0d6a1e46cb7997fab9194ec5a5d4b` 的 `handle_raw` 将原始 method/params 交给 `lan_request_direct`；`miio_command` 只解析 JSON 并提取 `result`。没有总流量 ×2 或升/毫升转换。详见 [客户端证据](evidence/mit-client.md)。该提交的源码检查不能替代对用户已安装二进制版本的校验。

**待验证**：3600L 的确切来源（耗材标称、设备标签、米家界面或其他版本）、7200 的单位及计量边界。不能把 `7200=2×3600` 自动解释成固件按 1:1 纯废水比累计原水。

新增插件中没有找到 3600/7200 的源码字面量，也没有找到针对滤芯 usedflow/totalflow 的 ×2 或纯废水比换算。历史水量页面另有除以 1000 显示 L 的逻辑，但该逻辑不接收滤芯 usedflow，不能借其认定 usedflow 是 mL。

质量守恒仅能给验证模型：在同一稳定制水区间、无其他储水变化时，`V原 ≈ V纯 + V废`。若纯:废=1:1，原水约为纯水的 2 倍；若为 2:1，则约为 1.5 倍。冲洗、启停、储水变化会改变区间关系。以上是物理模型，**不是恢复的固件公式**。

## 静态追踪

以下 VA 的原文件偏移为 `VA - 0x40201000`；装载依据见 [firmware.md](firmware.md)。

| 证据 | 函数 VA / 原文件偏移 | 观察 |
|---|---|---|
| S1 | `FUN_4024CE54` / `0x4BE54` | 注册 15 项 `miIO`、1 项 `user.bind_key`；没有 get_prop、滤芯/TDS 处理器。表在原文件 `0x6D980`，完整解析见 interfaces.json |
| S2 | `FUN_402488F4` / `0x478F4` | UDP 接收解析 method/params，查 `_JsDlgt`/`_JsDlgtS`；未命中则在 `0x40248EA9` 调用 `FUN_4024C4F4` |
| S3 | `FUN_40245E6C` / `0x44E6C` | TCP 路径同样处理；未命中在 `0x4024667D` 调 `FUN_4024C4F4` |
| S4 | `FUN_4024C4F4 → FUN_4024C2D8 → FUN_4024CBFC` / `0x4B4F4 → 0x4B2D8 → 0x4BBFC` | 请求文本复制进 MCU 下行队列，复制长度由文本长度决定；并保存应答回调，不区分水务属性 |
| S5 | `FUN_4024B89C`、`FUN_4024CD0C` / `0x4A89C`、`0x4BD0C` | `get_down` 将 JSON 的 method 和 params 提成 `down <method> <args>`；仅去除参数数组外层，不做数字水量运算 |
| S6 | `FUN_4024B278` / `0x4A278` | `json_get_down` 输出 `json_down <原请求>`；原文件 `0x6F189` 的格式字符串和 `0x6D92C` 的表项可复核 |
| S7 | `FUN_4024B4E8` / `0x4A4E8` | MCU 串口 `result` 的参数用 `%s` 拼成 `{"result":[... ]}` 后调用所保存回调；无滤芯算法 |
| S8 | `FUN_4024B1B4` / `0x4A1B4` | `json_ack` 直接把 MCU JSON 文本及长度交给回调 |
| S9 | `FUN_4024E0C0 → FUN_40244068` / `0x4D0C0 → 0x43068` | 串口文本追加 CR（`0x0D`）并逐字节送串口 0 |

对应 [反编译 C 文件](evidence/decompiled/) 及 [关键指令](evidence/bridge-calls.txt) 均保留。S2/S3 + S1 说明未注册的 `get_prop/set_*` 会进入桥接路径；并非仅凭字符串缺失推断。

桥接应答的等价摘录（分析注释，非厂商源码）：

```c
// FUN_4024B4E8, 原文件 0x4A4E8
// MCU 已把值作为串口参数提供；逐项文本拼接。
snprintf(buf, 0x400, "{\"result\":[%s", argv[1]);
// 后续参数仍用 %s 附加；最后补齐 JSON，再调用请求回调。

// FUN_4024B1B4, 原文件 0x4A1B4
reply.text = argv[1];
reply.length = strlen(argv[1]);
pending.callback(&reply, pending.context);
```

这个结论仅覆盖所恢复的通用桥接路径，不能推导“整个 MCU 没有换算”。

Wi-Fi 的 `props` 是 MCU→网络动态上报：`FUN_4024BB84 → FUN_4024D5B0 → FUN_4024D28C` 按属性名/值更新 RAM 链表，`FUN_4024D1A4` 复制属性字符串。该缓存不是已确认的滤芯持久化记录；其存在也不表示 `get_prop` 从缓存读值。

`miIO.info` 中唯一容易误判的 `life`（原文件字符串 `0x6E43F`）来自 `FUN_40240F28 → FUN_40241BFC → FUN_40241B60` 的运行 tick 计时及回绕处理，**不是滤芯寿命**。

## 可验证的只读方案（未执行）

1. 保留本次八项 get_prop 命令，每次记录时间、完整请求、返回数组和用户手动观察的工况。用户 U4 实测 run_status/rinse 在制水和不制水时均为 0，不能用二者自动标记制水状态，见 [状态证据](evidence/operating-state.md)。只用用户已有本地缓存凭据，不导出 Token。先单独重读 `f1_totalflow`、`f2_totalflow` 以核对字段对应；不试任何 setter 或 reset。
2. 在设备闲置、用户正常取水前后分别取样；正常取水结束后继续低频读取数次，辨别是即时、整数升量化、停机更新还是上报延迟。不要把一次短取水后不变当成没有计量。
3. 对用户原本要进行的正常取水，同期记录纯水量；在无需拆机或改水路且有现成测量条件时记录废水量/进水量。记录 F1/F2 差分 `ΔC1/ΔC2`，比较 `ΔC/V纯` 和 `ΔC/(V纯+V废)`。单位/缩放未知时保留比例，不能先固定为 L。
4. 被动观察自然发生的冲洗及空闲区间，检查哪一计数变化。不发送冲洗命令，也不专门切换模式。若没有这种自然数据，则“是否含冲洗”继续待验证。
5. 对时间字段，在不改变设置的前提下跨小时/跨日读数，检验 8640/17280 是否小时配额。使用时间是否按日历或制水时长累计须分别观察。
6. 固定纯废水比例且计数单位未知时，多种模型可能等价；需要不同自然工况或原始传感器证据，不能只用 `ΔC1/ΔC2≈2` 定案。不要用重启/断电/滤芯复位测试持久性。
7. 插件还揭示纯水历史事件和日/周/月统计，可在合法认证客户端中只读查询，与 usedflow 跳变对照。事件水量是设备上报值，不是独立体积测量；先核对记录格式和单位，不能把日统计或缺失值当作传感器原始数据。具体 type/key 及解析函数见 plugin.md。
